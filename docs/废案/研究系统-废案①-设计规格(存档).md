## 一、为什么不需要抄 GT 的研究站

GTCEu 自己的 `ResearchManager` / 研究站是一套**围绕"扫描物品→产生研究进度→解锁配方"**的专用系统，
和我们的需求错位。但它底层用的通用机制我们**可以直接复用**：

| 能力 | GTCEu 现成 API | 用途 |
|---|---|---|
| 配方挂"不满足就不跑"的条件 | `GTRecipeBuilder.addCondition(RecipeCondition)` | 锁定配方 |
| **启动后动态给已有配方加条件** | 遍历 `server.getRecipeManager().getAllRecipesFor(type)` 改 `recipe.conditions` | 不用改每条配方 JSON |
| 自定义条件类型 | 实现 `RecipeCondition` + 注册 `RecipeConditionType` | 自带 tooltip / 序列化 / 网络同步 |
| 配方挂自定义元数据 | `GTRecipeBuilder.addData(String, ...)` → `recipe.data` | 标"这条属于哪个研究" |
| 失败原因显示 | `MultiblockDisplayText.addRecipeFailReasonLine` | 玩家能看到"缺 XX 研究" |

**本项目已有同款先例**：[`VacuumRecipeInjector.java`](../src/main/java/org/ringclouds/gtnecore/recipe/VacuumRecipeInjector.java)
就是在服务器启动/重载时扫已加载配方、动态塞 `RecipeCondition`。本系统照这个模式做。

**结论**：不碰 GT 的 `ResearchManager`，自建一套轻量研究层，只借用上面这几个通用扩展点。

## 二、数据模型：**两段式**（用户 2026-09-26 定的方向）

> **旧方案已废弃**：原来让配方自带一个 `gtnecore:research` 数据键，配方作者得去改每条配方。
> 改为两段式后 **配方本体一个字都不用改**，且配方 id 是脚本作者本来就熟悉的东西。

```
① 注册研究条目（启动阶段）        ② 按配方 ID 归类（服务端）
   GtneResearch.register(...)       ResearchRecipeInjector.inject()
   声明"有这么一项研究"             扫配方管理器，命中的挂条件
   +"它管哪些配方 id"                        │
            │                                ▼
            └──────────────►  GtneResearchCondition（未完成则机器不跑）
```

### 2.1 注册层（启动阶段）—— `GtneResearch`

```java
// Java（Gtnecore 构造器里的 bootstrapBuiltin()）
GtneResearch.register("basic_metallurgy", "gtnecore.research.basic_metallurgy",
        "gtceu:macerator/*", "gtceu:arc_furnace/*");

// KubeJS（StartupEvents 或任意启动期脚本）—— 这是"接 KJS 方便"的落点
const Research = Java.loadClass('org.ringclouds.gtnecore.research.GtneResearch')
Research.register('basic_metallurgy',
    'gtnecore.research.basic_metallurgy',
    'gtceu:macerator/*', 'gtceu:arc_furnace/*')
```

**配方匹配规则**（`GtneResearch.RecipePattern`）：

| 写法 | 含义 |
|---|---|
| `gtceu:macerator/macerator_aluminium_ingot` | **精确**匹配这一条 |
| `gtceu:macerator/*` | **前缀通配**，匹配该前缀下全部配方 |

- 匹配是**大小写敏感的全等 / 字符串前缀**，可预测、好排查
- **刻意不用正则**——正则写错会静默锁掉一堆不该锁的配方，这类问题极难查
- 一条配方只归**一个**研究：多项都命中时以**先注册的**为准（注册顺序即优先级）
- 同 id 重复注册 = **覆盖**（方便脚本覆盖内置条目）

### 2.2 归类层（服务端）—— `ResearchRecipeInjector`

服务端启动 / `/reload` 后扫全部配方：

1. 对每条配方问 `GtneResearch.researchFor(recipe.id)` —— 命中哪个研究
2. 命中的补一个 `GtneResearchCondition`（列表不可变时反射换可写副本）
3. 日志**按研究分组**打印命中清单，便于核对"我锁的到底是不是这些"

**为什么必须在服务端**：`recipe.id` 是 `ResourceLocation`，**只在服务端存在**
（客户端收到的配方没有 id）。挂上的条件会随配方同步到客户端，所以 JEI 照样能显示。

**逃生口**：配方自带 `data` 里的 `gtnecore:research` 键优先级**高于** id 归类。
两段式之后基本用不到，留着应对"配方 id 会变"或"想单独指定"的情况。

### 2.3 配置层（数据包 JSON）—— ⏳ 未做

将来要支持数据包扩展时，形如 `data/gtnecore/research/<id>.json`：

```jsonc
{
  "title": "gtnecore.research.advanced_alloy_smelting",
  "prerequisites": ["basic_metallurgy"],
  "recipes": ["gtceu:alloy_smelter/*", "gtceu:arc_furnace/*"],
  "cost": [ { "item": "gtceu:aluminium_ingot", "count": 64 } ],
  "duration": 1200, "eu": 32
}
```

加载时机与 `GtneResearch.register` 一致（启动期），只是数据来源换成数据包。
**图校验**（前置都存在 + 无环）也在这一步做——现在 `prerequisites` 字段已留，未校验。

### 2.4 进度层（**先做世界级共享**）

> **决策变更（2026-09-26）**：用户要求"先不做团队共享的机制，先实现研究更好些"。
> 团队共享是**乘法复杂度**（FTB Teams 是 ARR → 只能反射软适配 + 回退），
> 核心价值在"配方能被研究解锁"这件事本身，所以先砍掉这一层。

```java
public final class ResearchProgress extends SavedData {
    boolean isCompleted(@Nullable ResourceLocation research);
    boolean complete(ResourceLocation research);
    boolean revoke(ResourceLocation research);      // 调试用
    Set<ResourceLocation> all();
}
```

- 存档级共享，落在**主世界**的 dataStorage（`Level.OVERWORLD`），多人时全员共用一份
- 骨架参考 [`HaloUnlockData`](../src/main/java/org/ringclouds/gtnecore/halo/HaloUnlockData.java)，
  但**去掉 UUID 维度**——那是按玩家永久解锁，语义不同
- 解析失败的条目静默忽略，坏存档不会卡住加载

**将来要做团队共享时**（S7）：加一个 `ResearchProgressStore` 抽象，
默认实现就是现在的世界级；FTB Teams 版本走反射，拿不到就静默回退。
**届时 `ResearchProgress` 的公开方法签名可以保持不变**，所以现在不做抽象层也不会返工。

**FTB Teams 兼容注意事项**（留档）：
- ARR 许可 → **不能** jarJar、不能硬依赖、不能编译期引用
- 走反射探测 + 调用，集中在一个类里（只在一处出现 `Class.forName`）
- `mods.toml` 里可选依赖也先不加

## 三、配方锁定：`ResearchCondition`

### 3.1 条件本身

```java
public class GtneResearchCondition extends RecipeCondition<GtneResearchCondition> {
    private final ResourceLocation research;

    @Override
    public RecipeConditionType<GtneResearchCondition> getType() { return GTNEcoreRecipeConditions.RESEARCH; }

    @Override
    protected boolean testCondition(GTRecipe recipe, RecipeLogic logic) {
        // 只有服务端会真正判定
        ServerLevel level = ...;               // 从 logic.getMachine() 拿
        return ResearchProgress.of(level).isCompleted(level, playerOf(logic), research);
    }

    // ⚠ 下面三个必须自己覆写，不能靠基类 —— 见 3.4
    @Override public String getTranslationKey() { ... }
    @Override public IGuiTexture getInValidTexture() { ... }
    @Override public IGuiTexture getValidTexture() { ... }

    @Override
    public Component getTooltips() {
        return Component.translatable("gtnecore.research.locked", titleOf(research));
    }

    @Override
    public GtneResearchCondition createTemplate() { return new GtneResearchCondition(); }
}
```

**命名注意**：GTCEu 自己已有 `gtceu:research` 条件（`com.gregtechceu.gtceu.common.recipe.condition.ResearchCondition`，
服务于 GT 研究站）。我们的 id 用 `gtnecore:research`，**类名也不要用 `ResearchCondition`**，
避免与官方那个撞名。

### 3.2 注册（时机已确认 ✅）

`GTRecipeConditions` 的 `<clinit>` 字节码实证：

```
RECIPE_CONDITIONS.unfreeze()
  → 注册官方条件（biome / dimension / cleanroom / **官方 research** / ...）
  → ModLoader.postEvent(GTCEuAPI.RegisterEvent<RecipeConditionType>)
  → RECIPE_CONDITIONS.freeze()
```

**与 `recipe_capability` 完全同构**（见废案一号 §二·坑 4）。所以项目里已有的写法直接可用：

```java
// Gtnecore.java：与现有的 GTRecipeType 监听并列
modEventBus.addGenericListener(
        com.gregtechceu.gtceu.api.recipe.condition.RecipeConditionType.class,
        GTNEcoreRecipeConditions::onRegister);
```

（也确认了 `IGTAddon` 里**没有** `registerRecipeConditions()` 钩子，
所以走 Forge 的 generic listener，而不是 addon hook。）

### 3.3 怎么挂到配方上

**两种来源，按优先级**：

1. **显式**：配方 JSON / KubeJS 里自己写 `"conditions": [{"type":"gtnecore:research","research":"xxx"}]`
2. **隐式（主力）**：研究定义里声明 `recipes`，启动时由注入器写入 `recipe.conditions`
   —— 配方作者不需要知道研究系统的存在

**注入点**：模仿 `VacuumRecipeInjector`，挂 `TagsUpdated` / `AddReloadListenerEvent` +
`ServerStartedEvent`，保证 `/reload` 后重新注入。

### 3.4 玩家上下文从哪来

`testCondition(recipe, logic)` 只有 `RecipeLogic`，**没有玩家**。三个可选来源：

| 来源 | 适用 | 备注 |
|---|---|---|
| 机器归属者（`IOwnedMachine` / 所有权系统） | 单人机器 | GTCEu 有 owner 机制，调研确认接口 |
| 机器所在队伍的成员 | 多人 | 需要 FTB Teams，回退时用世界级共享所以不需要玩家 |
| **退回世界级共享** | 全部 | `WorldProgressStore` 忽略玩家参数 → 天然无此问题 |

因为**当前整合包回退到世界级共享**，v1 不需要解决"玩家从哪来"这个问题。
将来接 FTB Teams 时，优先用"机器归属者队伍"，其次"最近交互的玩家"。

## 四、研究机器

### 4.1 形态

**多方块**（你选的）。设计要点：

- 大小：待定（`??×??×??`），先做 **3×3×3** 级别的小型结构，能跑通再加层
- 部件：能源仓（研究要耗电）、输入总线/仓（投研究材料）、**维护仓不要**（与恒星一致）
- 核心方块：一个"研究核心"（可复用的新方块），中间放它
- 外观：先复用现成机壳 + overlay 模型，别一开始就做自定义模型

### 4.2 运行逻辑（走配方系统，别手工 tick）

**这是本次的硬性要求**——人造恒星那次的教训（废案一号 §一）：
手工 `subscribeServerTick` 自己取仓/自己消耗，与 GTCEu 机器模型不一路。

所以研究机器也做成**配方驱动**：

- 一条 `gtnecore:research` 配方类型
- **未完成的研究 = 一条动态生成的配方**（`ICustomRecipeLogic`）：
  - 输入 = 该研究的 `cost`
  - 时长 = `duration`，EU = `eu`
  - 完成时把研究标记为已完成（`onRecipeFinish` 或 IO 钩子）
- 已完成的研究不再生成配方 → 机器空转
- 研究图的前置不满足 → 不生成配方，并在 UI 提示缺哪个前置

这样成本/时长/EU 全部由配方系统处理，**我们只写"生成哪条配方"和"完成时记一笔"**。

### 4.3 UI

- 主面板：当前正在研究什么 + 进度条（GTCEu 自带进度显示）
- 一个**选择研究**的界面：列出可研究的项目（前置已满足且未完成），显示成本
  - 参考人造恒星那个 `StarStatusConfigurator`（`IFancyConfigurator` 点开式面板），
    那套代码虽然随恒星撤了，做法在废案一号 §三·3.6 有记录
- 缺前置/材料时给出明确文案，别让玩家猜

## 五、JEI/XEI 表现：可见但锁着

已确认选「可见但锁着」。实现：

1. 配方**照常出现在 JEI 里**（不做任何隐藏处理）—— 这是最省事的方案
2. 锁定的配方在 JEI 页面上叠加一个**锁定角标**
3. tooltip 追加一行：`需要研究：<研究名>`（来自 `ResearchCondition.getTooltips()`）
4. 游戏内机器里跑不了 → `RecipeLogic` 会走 `setWaiting(条件文案)`，
   GTCEu 自带 `addRecipeFailReasonLine` 会把原因显示在机器 UI 上

**实现手法（待验证）**：GTCEu 的 JEI 分类渲染配方时会调用 `RecipeCapability` 之外的一层
widget 构建流程；锁定角标最可能挂在
`GTRecipeType.setRecipeUI(...)` 或 `RecipeCondition.getInValidTexture()`。
**`RecipeCondition` 自带 `getInValidTexture()` / `getValidTexture()`** ——
大概率就是给这个用的，实施时先验证这一条，能省掉自定义渲染。

## 六、分阶段实施

**每一步都可独立验收，不要一口气全做完再测。**

| 阶段 | 内容 | 验收 |
|---|---|---|
| **S1 · 数据层** | `ResearchDefinition` 解析 + `ResearchRegistry` + 图校验（环检测） | `/reload` 后 `/gtnecore research list` 能列出全部研究 |
| **S2 · 进度层** | `ResearchProgressStore` 接口 + `WorldProgressStore`（SavedData） | 手动调 API 标记完成后重登仍在 |
| **S3 · 条件层** | `ResearchCondition` + 条件类型注册 + 配方注入器 | 给一条现成配方挂研究条件，未完成时机器不跑且 UI 显示原因 |
| **S4 · 研究机器** | 多方块结构 + 配方类型 + 动态配方 + 完成回调 | 投料 → 进度条走完 → 研究完成 → 目标配方解锁 |
| **S5 · 界面** | 选择研究的面板 + 前置/成本显示 | 能看出"能研究什么、缺什么" |
| **S6 · JEI 锁定角标** | 叠加图标 + tooltip | JEI 里可见但标着锁 |
| **S7 · FTB Teams 软适配** | 反射层 + `FtbTeamsProgressStore` | 装了 FTB Teams 时按队伍共享；不装时行为不变 |

**先做 S1–S3 就能验证整条链**（条件 + 注入器用现有机器就能测），
不必等机器做出来。建议按这个顺序推进。

## 七、待定 / 需要你拍板的点

1. **研究机器的大小与结构**：先 3×3×3 小型？还是你想直接给个大结构
2. **研究成本怎么定**：先用占位数值（如 64 锭 + 8000mB 流体 + 1200t），
   等研究清单列出来再逐个配
3. **研究清单本身**：你打算锁哪些配方？先给 3–5 条做验证，还是一次列全
4. **前置是"与"还是"或"**：v1 建议只做"与"（全部前置完成才可研究），
   "或"的需求等真有再加
5. **研究可否并行**：一台机器同时只做一个研究（建议），还是支持排队

## 八、与既有系统的关系

- **不动 GTCEu 的 `ResearchManager`**，两套并存互不干扰
- **不动 GT 的研究站配方**（`scannerResearch` 等）—— 那些照旧能用
- 研究条件和 `VacuumRecipeInjector` 加的真空条件是**正交的**，可以同时挂在一条配方上
- 存储骨架参考 `HaloUnlockData`，但**不共用**（那是按玩家 UUID 的永久解锁，语义不同）
