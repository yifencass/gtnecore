## 一、撤除前的架构（本身是好的，值得复用）

**两段式**（用户点名的方向，比最初方案好）：

```
① 注册研究条目（启动阶段）            ② 归类（服务端，配方已加载后）
   GtneResearch.register(...)           GtneResearch.of("chemical")
   只声明"有这么一项研究"                    .addAll(GTRecipeTypes.CHEMICAL_RECIPES)
            │                                        │
            └──────────────►  GtneResearchCondition（未完成 → 机器不跑 / JEI 标"需要研究"）
```

**三个入口**：

| API | 用途 |
|---|---|
| `register(id, titleKey[, 前置...])` | 注册条目，返回 `ResearchCategory` 可链式 |
| `of(id).add(配方id)` | 单条；末尾 `*` 当**前缀通配** |
| `of(id).addAll(配方类型[, 过滤器])` | **整类配方** ← 用户伪代码里那句 |

**关键设计**：**配方本体一个字都不用改**——归类靠扫配方管理器按 id 匹配，
而不是让每条配方自带数据键。这是相对最初方案的实质改进。

## 二、撤除的直接原因：**条件键名撞车** ★

```
java.lang.IllegalStateException: [register] registry gtceu:recipe_condition
        contains key research already
    at GtneResearchConditions.register(GtneResearchConditions.java:49)
    at GtneResearchConditions.onRegister(GtneResearchConditions.java:41)
```

**原因**：GTCEu **自己已经注册了 `research` 这个条件键**
（`com.gregtechceu.gtceu.common.recipe.condition.ResearchCondition`，
服务于 GT 的研究站）。我在自己的设计文档里甚至专门写了「命名注意：GTCEu 已有
`gtceu:research`」，**结果注册时键名还是用了 `research`** —— 纯粹的疏忽。

**修法（一行）**：注册名换成不会撞的，例如 `gtnecore_research`。
`GTRegistries.RECIPE_CONDITIONS` 的键空间是**全局扁平**的，不是按 modid 隔离的：

```java
// ❌ 撞 GTCEu 自带的 research
GTRegistries.RECIPE_CONDITIONS.register("research", type);

// ✅ 带前缀，确保唯一
GTRegistries.RECIPE_CONDITIONS.register("gtnecore_research", type);
```

**教训**：GTCEu 的 `GTRegistry.String` 类注册表（recipe condition / recipe capability /
chance logic / recipe condition type / sound …）**键是全局的**，
注册前先 `GTRegistries.XXX.containKey("名字")` 查一下，或者干脆一律加 modid 前缀。

## 三、之前踩过并已解决的坑（重做时别重踩）

### 坑 1 · 条件类型注册时机（**已核实 ✅**）

`GTRecipeConditions.<clinit>` 字节码：

```
RECIPE_CONDITIONS.unfreeze()
  → 注册官方条件（biome / dimension / cleanroom / **官方 research** / ...）
  → ModLoader.postEvent(GTCEuAPI.RegisterEvent<RecipeConditionType>)   ← 在这里注册
  → RECIPE_CONDITIONS.freeze()
```

与 `gtceu:recipe_capability` 完全同构。所以走 Forge generic listener：

```java
modEventBus.addGenericListener(
        com.gregtechceu.gtceu.api.recipe.condition.RecipeConditionType.class,
        GTNEcoreRecipeConditions::onRegister);
```

⚠ `IGTAddon` **没有** `registerRecipeConditions()` 钩子（已核实），别去找。

### 坑 2 · `RecipeConditionType` 没有 name 字段

其 `toString()` 是 Object 默认实现，于是基类的默认实现会拼出**无效路径**：

```java
// 基类默认（有坑）
getInValidTexture() { return new ResourceTexture("block/condition/" + getType() + "_invalid"); }
//                                                            ^ 对象地址
getTranslationKey() { return "gtceu.recipe.condition." + getType(); }
```

**所以自定义条件必须自己覆写** `getInValidTexture()` / `getValidTexture()` / `getTranslationKey()`。

### 坑 3 · 条件 codec 别用 `RecipeCondition.isReverse(inst)`

那个写法在 Java 泛型推断上**过不去**（`Mu<RC>` 与 `RC` 无法统一）。
改用 `RecordCodecBuilder.mapCodec` + `Codec.BOOL.optionalFieldOf`：

```java
public static final Codec<MyCondition> CODEC =
        RecordCodecBuilder.<MyCondition>mapCodec(inst -> inst.group(
                Codec.BOOL.optionalFieldOf("is_reverse", false).forGetter(MyCondition::isReverse),
                Codec.STRING.optionalFieldOf("field", "").forGetter(MyCondition::getField)
        ).apply(inst, (rev, f) -> { ... })).codec();
```

### 坑 4 · 同事件的多个监听器**顺序不确定**

我一开始让「归类」和「注入」各自监听 `ServerAboutToStartEvent`，还在注释里写"靠注册顺序保证"
—— **错的**。一旦注入先跑，那一轮就锁不住任何配方（要等重启才生效）。

**修法**：合成一条**确定的流水线**，一个类接事件、按顺序调：

```
清已处理标记 → 清旧成员 → 归类 → 注入
```

### 坑 5 · 配方条件列表对 JSON 配方是**不可变**的

JSON 反序列化出来的配方，`conditions` 是 `List.copyOf` 的不可变列表，
直接 `add` 抛 `UnsupportedOperationException`。
照 `VacuumRecipeInjector` 的办法：原地写失败 → **反射换可变副本**
（`GTRecipe.conditions` 是 public final 字段，Java 17 允许对其实例写入）。

### 坑 6 · `recipe.id` **只在服务端存在**

客户端收到的配方没有 id，所以**归类只能在服务端做**。
挂上的条件会随配方同步到客户端，JEI 因此也能显示"需要研究"。

## 四、一个"免费"的发现（值得记住）

**JEI 里显示"需要 XX"是免费的。**

`GTRecipeWidget` 对**所有** `RecipeCondition` 一视同仁地渲染 `condition.getTooltips()`。
这一点由本项目的 [`VacuumRecipeInjector`](../../src/main/java/org/ringclouds/gtnecore/recipe/VacuumRecipeInjector.java)
在实战中确认（它给电路装配机注入真空条件后，配方页自动多出"需要真空环境"）。

所以**不需要**碰 XEI 渲染就能显示锁的原因。只有"锁定角标图标"才需要额外处理
（走 `getInValidTexture()`）。
