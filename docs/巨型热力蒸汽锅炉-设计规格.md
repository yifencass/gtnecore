# 巨型热力蒸汽锅炉 设计规格

> 状态：**⏸ 仅设计，暂不实现**（2026-09-26）
> 定位：多方块蒸汽锅炉，复用 PneumaticCraft 的气压逻辑做「压力门槛 + 超压自爆」
> 依赖：`PneumaticCraft-集成规格.md`（API 清单与许可边界）
>
> **本文件是设计存档，不是开发计划。** 留待将来灵感更新时再定稿 ——
> 文中的 `??` 待填项、"待核实"、"必须先验证"均为**设计期的自我提醒**，
> **不是待办事项**，不要按它开工。
>
> **单位约定（务必遵守，别再搞错）**
> - 文档中"度"一律指**摄氏度**
> - **代码中一律使用开氏度**（PnC 热系统用 K），换算 `K = °C + 273.15`
> - 压力单位一律 **bar**
>
> 核心原则：**蒸汽容积是唯一的池子。`bar` 是它的读数，产出从池中取走容积，
> 因此产出必然间接降压 —— 高品位必须靠持续投入燃料维持。**

## 一、核心模型

```
                    ┌───────────────────────────────┐
   蒸馏水 ─────────▶│         流体输入仓            │
                    └───────────────┬───────────────┘
                                    │
                     加热（速率 = η(T)，温度不消耗）
                                    │
                                    ▼
                    ┌───────────────────────────────┐
                    │    蒸汽容积 · 唯一的池子      │
                    └───────────────┬───────────────┘
                                    │
              ┌─────────────────────┴─────────────────────┐
              │                                           │
      产出蒸汽取走容积                              求商（不取走）
              │                                           │
              ▼                                           ▼
┌───────────────────────────┐               bar = 蒸汽容积 / 容积
│ 蒸汽 / 超临界 / 超超临界  │                              │
│ / 先进超超临界（专用接口）│                              ▼
└───────────────────────────┘                    硬门槛 · 安全状态
              │
              └─ 取走后池子变少 → bar 随之降低
```

图中有意区分两条支路：

- **左支「取走容积」** —— 产出蒸汽**消耗**池子，取走后 `bar` 随之降低
- **右支「求商」** —— `bar` 只是由池子**算出**的读数，**不占份额、不消耗**

**关键：`bar` 是算出来的读数，不占份额；产出才是真正取走蒸汽容积的那一方。**

- 温度不消耗，它只决定**水变蒸汽容积有多快**（η(T)）
- 压力不消耗，它是 `蒸汽容积 ÷ 容积` 的商
- **产出取走蒸汽容积 → (a) 池子变少、(b) bar 随之降低**（两个独立后果，不是反馈环）

**水只有一个去处：进流体输入仓被烧。** 没有"直接灌水提压"这回事。

**压力与蒸汽容积不是两个池子，也不存在分配 —— 前者是后者的读数。**

### 1.1 各环节的角色

| 环节 | 角色 | 由什么决定 |
|---|---|---|
| **流体输入仓水量** | 能不能产（原料） | 玩家投料 |
| **η(T)（转换效率）** | 水 → 蒸汽容积的**产出速率** | 温度 |
| **蒸汽容积** | **唯一的池子**。既是压力读数，也是产出储备 | 烧水累积 |
| **容积（volume）** | 压力室的额定容量，决定**压力标尺** | 结构 / 容积升级 |
| **bar = 蒸汽容积 / 容积** | **硬门槛** + 安全状态 | 由上面两者推出 |

### 1.2 ★ 池子水位即压力，产出必然降压

因为 `bar` 就是池子的读数，**任何从池中取走蒸汽容积的行为都会降压**：

```
   蒸汽容积被抽走 ──→ bar 下降 ──→ 可能跌出高品位门槛
        ▲                              │
        │                              ▼
        └──── 必须烧更多水补回 ←─── 燃料成本上升
```

推论：**高品位不是"设好了就永久拥有"的状态，而是"持续投入燃料才维持得住"的运行工况。**
压力门槛越高，维持成本越贵。

两个细节展开：
- **产出抽取与维持的平衡点** → §4.3
- **扩容如何改变这笔账** → §4.2

### 1.3 PnC API 的贴合度

`IAirHandler` 的 javadoc 给出：

```
amount of air = pressure * volume        // getAir() = getPressure() * getVolume()
```

即"加压 = 灌空气"。**我们的"蒸汽容积"就直接对应 PnC 的"气量（air）"**：

```
烧水 ──→ addAir(蒸汽容积)          // 池子进水
bar  ──→ getPressure()            // 直接就是我们的硬门槛读数
扩容 ──→ setBaseVolume(...)       // 插容积卡瞬间降压（见 §4.2）
产出 ──→ addAir(-取出量)          // 流出即降压（见 §4.3）
```

映射是自然的：**四个操作恰好一一对应**。所以 PnC 的 air handler 在语义上贴合，
是否采用见 §7.2 评估（取决于是否需要它的测压计读数）。

## 二、温度和压力的分工

### 2.1 温度不直接决定压力，它决定池子进得多快

```
温度 ──→ η(T) ──→ 烧水出蒸汽容积的速率（池子进水速度）
温度 ──→ 蒸汽等级资格（硬门槛，见 §3）
```

温度**不封顶压力**，也不产生压力 —— 它决定**原料被烧成蒸汽容积有多快**。
而 bar 是池子水位的读数，因此 bar 的实际水平取决于三者的平衡：

| 因素 | 对 bar 的作用 |
|---|---|
| **η(T)**（温度） | 池子进水速度 → 决定能否补上被抽走的部分 |
| **蒸汽容积存量** | bar 的分子 |
| **容积（volume）** | bar 的分母 —— 容积越大，同存量下 bar 越低 |
| **产出抽取** | 池子出水 → **间接降压**（见 §4.3） |

两个旋钮各管一件事，不冗余：

- 水多了但温度不够 → η(T) 低，池子进得慢，bar 涨不动
- 温度够了但水断了 → 池子断供，且产出还在抽，**bar 会往下掉**

### 2.2 ★ 压力是硬门槛

**温度与压力必须同时达标**才能进入对应蒸汽等级。只满足其一只停在低等级。

这条是刻意设计的：压力既然是硬门槛，那么"顶压运行"就是拿高品位的必经之路，
而压力越高离自爆线越近 —— **推进与危险是同一个旋钮**。

## 三、蒸汽等级门槛

| 蒸汽等级 | 温度门槛（°C） | 温度门槛（K，代码用） | 压力门槛（bar） |
|---|---|---|---|
| **蒸汽** | < 350 | < 623.15 | ~0 |
| **超临界蒸汽** | **350** | **623.15** | **250** |
| **超超临界蒸汽** | **500** | **773.15** | **325** |
| **先进超超临界蒸汽** | **700** | **973.15** | **400** |

### 3.1 判定矩阵

压力列按**区间**取值（`bar` 落在哪个区间算哪一档）：

```
                        压力区间 →
                  [0,250)   [250,325)  [325,400)   ≥400
温度门槛 ↓          bar        bar        bar        bar
──────────────────────────────────────────────────────────
< 623.15 K         蒸汽       蒸汽       蒸汽       蒸汽
  (< 350°C)
623.15 K           蒸汽     超临界     超临界     超临界
  (350°C)
773.15 K           蒸汽     超临界   超超临界   超超临界
  (500°C)
973.15 K           蒸汽     超临界   超超临界     先进
  (700°C)
──────────────────────────────────────────────────────────
        温度不达标 → 无论压力多高都只出「蒸汽」
```

**读法**：温度与压力各自落在哪个档，取两者能共同满足的**最高**等级。
温度是"资格"（不达标直接封顶），压力是"档位"。

### 3.2 宽间距的两条实现要求

三个门槛之间留有大量中间地带：

```
350°C ──150K──→ 500°C ──200K──→ 700°C
```

这直接推出两条实现要求：

1. **档位判定必须带迟滞（hysteresis）**
   否则玩家在阈值附近反复加燃料时，输出流体会不停切换。
2. **自爆线必须在 973.15 K / 400 bar 之上留大余量**
   否则"满负荷运行先进超超临界"就等于站在自爆线上，缓冲区就白留了。
   → 自爆门槛定为 `??`（**待定**），建议留足一个整档余量。

## 四、蒸汽容积池（产出侧）

**产出消耗的不是 bar，而是蒸汽容积 —— 但因为两者是同一个池子，产出会间接降压。**

```
[蒸汽容积池]
     │
     ├── 按当前蒸汽等级兑换 ──→ 蒸汽 / 超临界 / 超超临界 / 先进超超临界
     │                          （经专用输出接口，不走气动管网）
     │
     └── 流出即降压 ──→ bar 下降 ──→ 可能掉出高品位门槛
                ▲
                └── 必须烧更多水补回（燃料成本）
```

- 池子按**结构当前的蒸汽等级**决定把容积兑换成什么流体输出
- 蒸汽容积**不是"灌水就涨"** —— 只有水进了流体输入仓、被温度烧过，才产生蒸汽容积
- 输出经**专用接口**，**不走气动管网**

### 4.1 这个设计解决了什么

若直接消耗 bar 计价，兑换率会变得荒谬：产 1 桶超临界蒸汽若吃掉 250 bar，
玩家等于在跟一个数值大得没法用的计价单位打交道，高压锅炉也会变成"一个超大压力存储罐"
而不是蒸汽源。

用**蒸汽等级做汇率**则正常：等级越高，每单位蒸汽容积换到的蒸汽越多（或换同样的蒸汽
只需更少容积）。**压力因此变成"品质门槛"而非"标价"。**

### 4.2 ★ 扩容的真实代价：维持同一个 bar 更贵

因为 `bar = 蒸汽容积 / 容积` 且容积在**分母**，扩容会把账算成两笔：

| | 大容积 | 小容积 |
|---|---|---|
| 达到**同一个 bar** 需要 | **更多蒸汽容积**（更多水 / 更高 η(T)） | 更少 |
| 同速率产出时 bar 的**相对**波动 | **更小** | 更大 |
| 满池时的 bar 上限 | **更低** | 更高 |

所以扩容**不是纯增益**，它的准确定位是：

> **用"更贵的压力维持成本"换取"抗产出抽取的稳定性"。**
> `bar 的维持成本 ∝ 容积`

- **插容积卡瞬间降压**：存量不变、分母变大 → bar 立刻掉
- **之后更难升压**：要回到原来的 bar，需要按新容积比例补更多蒸汽容积
- 换来的是：同样产出速率下，bar 掉得慢、不易跌破门槛

### 4.3 产出抽取与维持的平衡

产出的每一份蒸汽都从池中取走容积，因此存在一个**平衡点**：

```
η(T) 的补充速率  vs  产出抽取速率

补充 > 抽取  →  bar 上升（可够到更高门槛，但逼近自爆线 ⚠）
补充 = 抽取  →  bar 稳定在当前档位（理想工况）
补充 < 抽取  →  bar 下降（掉档，甚至跌回低品位）
```

**高品位 = 高维持成本**：门槛越高，需要的 η(T) 与投水量越大。
这就是"产蒸汽的代价是燃料"的精确形式。

## 五、超压自爆

**自己实现**（PnC 的爆炸逻辑在 `common` 包 = GPLv3 区域，不可引用；见集成规格 §3.3）。

### 5.1 判定链

```
bar 上升
  │
  ├─ bar < danger              → 正常
  ├─ danger ≤ bar < critical   → 危险区：enableSafetyVenting 主动泄压
  └─ bar ≥ critical
        ├─ 泄压足够          → 压回危险区以下
        └─ 泄压不足/被关闭   → 自爆
```

- `getDangerPressure()` / `getCriticalPressure()` 表达档位
- `enableSafetyVenting(FloatPredicate pressureCheck, Direction dir)` 做正常泄压
- 越过临界且泄压不足 → 触发自研爆炸

### 5.2 `maxPressure()` 与爆炸的关系

`IAirHandler.maxPressure()` 的 javadoc 明确：

> Behaviour when more air is added is implementation-dependent
> (e.g. items tend to stop accepting air, while blocks/machine tend to **explode**)

**注意**：api 里**没有** `setMaxPressure()` —— `maxPressure()` 是只读的
（实测：`api` 包内只有 `IAirHandler` 第 78 行声明，以及 `IClientRegistry.drawPressureGauge`
的渲染参数引用它）。它表达的是**这个容器能承受的上限**。

因为容器由我们自己实现，所以：

- `maxPressure()` 直接返回我们的 `critical` 值 → **超压线即上限**
- 爆炸在 `critical` 处触发，判定权完全在我们手里
- 若想留"危险区"（`danger` 到 `critical` 之间先泄压告警），
  就设 `danger < critical`，并在 `danger` 处启用 `enableSafetyVenting`

### 5.3 爆炸语义（自研，与 PnC 机器不同）

- **多方块解体**（不是单方块消失）
- **当量按压力**（越高压越猛）
- **自爆阈值随结构升级提高**（更好的压力容器能顶更高）

### 5.4 与「人造恒星不熔毁周围」设定的一致性

| 机器 | 事故行为 |
|---|---|
| 人造恒星（受控结构） | 正常运转与超新星**均不伤及周围** |
| 巨型热力蒸汽锅炉（压力容器） | **超压自爆伤及周围** |

**区分原则：受控结构不出事，非受控压力容器出事。**

## 六、管网隔离（必须遵守）

本锅炉的 bar 数值**不服务常规气动设备**，因此可自由放开到 400 bar 量级，
远超 PnC 自带的 7/12/25 bar 设备规格。

但因此产生一条**必须**遵守的纪律：

> PnC 的管道按「连接双方的压差」双向均衡输气。若锅炉在 400 bar 而普通压力管道标称 7 bar，
> 玩家接一根普通管道就是一次瞬时巨大压差灌入 —— 要么瞬间炸掉整条管线，要么数值算得乱七八糟。

**做法**：

- 锅炉使用**自有的高压管路/仓室**，`setConnectedFaces` 只列出本套管路
- **拒绝**常规 PnC 压力管道接入
- 蒸汽输出走**专用接口**，不走气动管网
- 玩家可复用 PnC 的**测压计读数**与**安全阀概念**，不是它的管道

网络均衡由 PnC 侧通过 `getConnectedAirHandlers()` 驱动；我们只负责把
`setConnectedFaces` 限定在自有管路上，**不在自身实现里做任何跨网络的均衡计算**。

### 7.2 ★ 压力状态挂哪个类型（设计期结论，留待将来实现时验证）

> ⏸ **本条不是待办**：因为本机暂不实现，这个"10 分钟验证"已并入将来的实现前置条件。
> 记在这里是为了让将来动手时不必重新推一遍。

`IAirHandler` 的四个核心操作与本锅炉语义**一一对应**（见 §1.3）：

| 本锅炉 | `IAirHandler` |
|---|---|
| 烧水入池 | `addAir(+)` |
| 压力读数 | `getPressure()` |
| 容积升级 | `setBaseVolume(...)` |
| 产出抽出 | `addAir(-)` |

也就是说 `bar = 蒸汽容积 / 容积` 与 PnC 的 `pressure = air / volume` **本来就是同一个公式**。

因此有两条路线：

| 路线 | 做法 | 代价 |
|---|---|---|
| **A. 用 PnC 的 handler** | `createAirHandler(myTier, volume)`，实现 `IAirHandlerMachine` | 要实现较多接口方法；但白得测压计兼容 |
| **B. 自维护数值** | 自己存 float 压力 + 自定义 `PressureTier` 仅作读数/档位 | 实现量小；但 PnC 测压计**可能读不到** |

**路线选择只取决于一件事：是否需要 PnC 测压计直接读本机压力。**

**倾向 B**：先按 B 做通内核（水→蒸汽容积→压力→产出→自爆），
若测压计兼容性确实要 A，再补上 —— 因为 A 只是把同一套数值挪到 PnC 的接口后面，
后补不会推翻内核逻辑。

**将来动手时的第一件事**：写个最小测试，看 PnC 测压计能否读一个不实现
`IAirHandlerMachine` 的机器。它决定状态机挂在什么类型上。
