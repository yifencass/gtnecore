# 模块化多方块部件 · 设计规格

> 状态：**设计稿**（2026-09-27）
> 依据：对 `build/patched/gtceu-1.20.1-7.5.3-patched.jar` 的三轮只读精读
> （`javap -p -c` 字节码 + 项目内 patch 源码 + Fernflower 反编译），全部关键结论**已验证**。
> 标注约定：**【已验证】** = 有字节码/源码证据；【推断】= 由已验证机制推出；【未验证】= 需实测。

---

## 一、问题定义

GTM 的多方块体系给了零件，**没给"模块"这层抽象**。三处症结：

1. **控制器靠 `instanceof` 硬编码**。`ThreadFurnaceMachine`：

```java
for (var part : getParts())
    if (part instanceof IThreadHatch hatch) list.add(hatch);   // 每加一种部件就改这里
```

2. **没有"一个部件 = 若干能力的组合"**。想同时提供线程+并行，只能 `implements IThreadHatch, IParallelHatch`。
3. **`PartAbility` 不是运行时能力**（见 §二），不能拿它当模块身份。

## 二、必须先搞清的两层（**这是设计的地基**）

### 2.1 第一层：能力位 = 结构槽（编译期方块快照）

```java
// PartAbility 的真实语义【已验证】
registry: Int2ObjectMap<Set<Block>>          // tier -> blocks
allBlocks = GTMemoizer.memoize(...)           // 记忆化！
register(tier, block)  = computeIfAbsent(tier, HashSet::new).add(block)
isApplicable(block)    = getAllBlocks().contains(block)
```

**`Predicates.abilities(...)` 根本不调用 `isApplicable()`**【已验证】：

```java
Arrays.stream(abilities).map(PartAbility::getAllBlocks)
      .flatMap(Collection::stream).toArray(Block[]::new)
  → blocks(Block...) → PredicateBlocks
// 匹配：ArrayUtils.contains(blocks, state.getBlock())
```

→ **能力位是"一组方块"，不是运行时能力协商。**

**⚠ 三个致命细节【已验证】：**

| 细节 | 后果 |
|---|---|
| `allBlocks` 是 `GTMemoizer.memoize`，**`PartAbility` 未暴露 `invalidate()`** | 首次读取后**永久冻结**，运行期无法刷新。所有 `register` 必须在注册期完成 |
| `PredicateBlocks.buildPredicate()`：`if (blocks.length == 0) blocks = {Blocks.BARRIER}` | **空能力位退化成"只接受屏障方块"**，结构永不成型且报错迷惑 |
| `PartAbility.getName()` 在全 jar 中被调用 **0 次** | 唯一标识是**对象引用**，重名无害 |

**不存在全局能力位列表**【已验证】（`PartAbilityRegistry`/`PART_ABILITIES`/`setAbilities` 命中数均为 0）→ 第三方 `new PartAbility("x")` 无需注册，但只对**持有同一实例引用**的 pattern 可见。

### 2.2 第二层：运行时部件 = `IMultiPart` 接口

`IMultiPart` 提供**完整的贡献钩子**【已验证】，且**不含任何 ability 概念**。

**结论：模块化的两层必须显式分开**

| | 是什么 | 何时生效 | 用什么表达 |
|---|---|---|---|
| **能力位** | 能不能放在某个结构字符位 | **pattern 首次构建时**（编译期快照） | `PartAbility` + `Predicates.abilities(...)` |
| **模块** | 成型后对控制器贡献什么 | **运行期**（每 tick 可查） | `IMultiPart` 的接口 + `instanceof` |

## 三、模块化设计

### 3.1 模块键与模块

```java
/** 模块类型令牌。一个部件可登记多个。 */
public interface PartModuleType<M extends PartModule> {
    String id();
    Class<M> view();
}

/** 模块实例。 */
public interface PartModule {
    /** 一个部件可同时提供多个模块 —— 这是"部件多功能"的落点。 */
    Collection<PartModuleType<?>> types();
}
```

具体模块（沿用项目已有的 `IThreadHatch` 直觉）：

```java
public interface ThreadModule extends PartModule {
    PartModuleType<ThreadModule> TYPE = PartModuleTypes.register("gtnecore:thread", ThreadModule.class);
    ThreadGrade grade();
    int threads();
}

public interface ThermalModule extends PartModule {
    PartModuleType<ThermalModule> TYPE = PartModuleTypes.register("gtnecore:thermal", ThermalModule.class);
    int heatCapacity();
    int maxTemperature();
}
```

### 3.2 部件侧

```java
public class ThreadHatchPartMachine extends TieredPartMachine
        implements IMultiPart, ThreadModule {          // 需要几个模块就 implements 几个

    @Override public Collection<PartModuleType<?>> types() { return List.of(ThreadModule.TYPE); }
    @Override public ThreadGrade grade() { return grade; }
    @Override public int threads() { return currentThreads; }
}
```

注册时**两层各自声明**：

```java
REGISTRATE.machine("thread_hatch", ThreadHatchPartMachine::new)
    .tier(tier)
    .abilities(GtneAbilities.THREAD)    // ← 第一层：结构槽（必须注册期完成）
    .modelProperty(GTMachineModelProperties.IS_FORMED, false)
    .register();                         // onRegister → PartAbility.register(tier, block)
// 模块信息不在这里声明 —— 靠 instanceof/composition 在运行期查
```

### 3.3 控制器侧：一次泛型查询取代 N 个 instanceof

```java
public final class Modules {

    @SuppressWarnings("unchecked")
    public static <M extends PartModule> List<M> of(IMultiController c, PartModuleType<M> type) {
        List<M> out = new ArrayList<>();
        for (IMultiPart part : c.getParts()) {
            if (part instanceof PartModule m && m.types().contains(type)) {
                out.add((M) m);
            }
        }
        return out;
    }

    public static <M extends PartModule> int sumInt(IMultiController c, PartModuleType<M> t,
                                                    ToIntFunction<M> f) {
        int s = 0;
        for (M m : of(c, t)) s += f.applyAsInt(m);
        return s;
    }

    public static <M extends PartModule> Optional<M> best(IMultiController c, PartModuleType<M> t,
                                                          Comparator<M> cmp) {
        return of(c, t).stream().max(cmp);
    }
}
```

`ThreadFurnaceMachine` 改写后：

```java
int threads = Modules.sumInt(this, ThreadModule.TYPE, ThreadModule::threads);
ThreadGrade grade = Modules.best(this, ThreadModule.TYPE,
        Comparator.comparingInt(ThreadModule::gradePriority))
        .map(ThreadModule::grade).orElse(ThreadGrade.NORMAL);
```

**加多少种部件，控制器这两行都不用动。**

## 四、模块可用的钩子全清单（**已验证的调用链**）

这是"模块能做什么"的边界。全部来自 `WorkableMultiblockMachine`【已验证】：

| 钩子 | 触发点 | 返回值语义 |
|---|---|---|
| `modifyRecipe(recipe)` | `doModifyRecipe` ← `fullModifyRecipe` ← `RecipeLogic.checkMatchedRecipeAvailable:214` / `onRecipeFinish:475` | **返回 `null` = 该配方对整机不可用**（否决） |
| `beforeWorking(ctrl)` | `RecipeLogic.setupRecipe:347`（**扣料之前**） | `false` → 状态 IDLE、进度清零 |
| `onWorking(ctrl)` | `RecipeLogic.handleRecipeWorking:241`（每 tick） | `false` → `interruptRecipe()` |
| `onWaiting(ctrl)` | `RecipeLogic.setWaiting:397` | 无返回值，纯通知 |
| `afterWorking(ctrl)` | `RecipeLogic.onRecipeFinish:457` / `interruptRecipe:509` | 完成/中断收尾（官方 `IMufflerMachine` 在此喷污染） |
| `onPaused(ctrl)` | `setWorkingEnabled(false)` | 仅"关闭工作"时 |
| `addMultiText(list)` | `IDisplayUIMachine.addDisplayText` 遍历所有 part | 往控制器屏幕写字 |
| `attachFancyTooltipsToController` | `WorkableElectricMultiblockMachine.attachTooltips:179` | 控制器 tooltip |
| `attachConfigurators(panel)` | 继承自 `IFancyUIMachine` | 控制器侧配置按钮（`IDistinctPart` 就这么做） |

⚠ **这些钩子只在控制器是 `WorkableMultiblockMachine`（或子类）时才被遍历调用**【已验证】——纯 `MultiblockControllerMachine` 不调。

**部件自己的 tick**：部件是 `MetaMachine`，可自行 `subscribeServerTick(...)`【已验证】。"每 tick 介入"的正确做法是部件自己的 tick 订阅，**不是**等控制器回调。

## 五、"部件向控制器提供能力"的两条通道

### 通道 A：配方能力（自动汇总）【已验证】

```java
// WorkableMultiblockMachine.onStructureFormed
for (IMultiPart part : getParts()) {
    IO io = ioMap.getOrDefault(part.self().getPos().asLong(), IO.BOTH);
    if (io != IO.NONE)
        for (RecipeHandlerList hl : part.getRecipeHandlers())
            if (hl.isValid(io)) { addHandlerList(hl); subscribe(hl); }
}
```

- 部件的 `getHandlerList()` 默认**从自身 traits 收集** `IRecipeHandlerTrait`，**IO 由第一个 trait 的 `getHandlerIO()` 决定**【已验证】。
- 空表 = `RecipeHandlerList.NO_DATA`（`IO.NONE`）→ 控制器直接跳过。
- ⚠ **`handlerList` 缓存无失效机制**【已验证】：运行中增删 trait 不会被控制器感知。要动态就**重写 `getRecipeHandlers()`**。
- 动态唤醒：`NotifiableItemStackHandler`/`NotifiableFluidTank` 等变化时 `notifyListeners()` → 控制器 `recipeLogic::updateTickSubscription`【已验证】。

### 通道 B：非配方能力（`addedToController` / `removedFromController`）

官方范式（`CleaningMaintenanceHatchPartMachine`，项目 `OmniMaintenanceHatchPartMachine` 是直接翻版）【已验证】：

```java
@Override
public void addedToController(IMultiController controller) {
    // 把自己的能力"挂"到控制器上（如注入 ICleanroomReceiver）
    super.addedToController(controller);      // ⚠ @MustBeInvokedByOverriders，必须调
}
```

## 六、控制器侧可用的扩展点

| 扩展点 | 用途 | 官方使用实例 |
|---|---|---|
| `shouldAddPartToController(IMultiPart)` | **准入闸门**：过滤掉不该当部件的匹配 | `CleanroomMachine`（排除被内包围的部件） |

## 七、主机 + 拓展子结构（空间站）—— 另一个需求

你要的"A 结构里 B 位匹配模块 B 的控制器"，用**官方 `slotName` 位置槽**实现。

### 7.1 机制【已验证】

```java
// SimplePredicate.checkInnerConditions 字节码
if (slotName != null) {
    Long2ObjectMap<Set<String>> slots = ctx.getOrCreate("slots", Long2ObjectOpenHashMap::new);
    slots.computeIfAbsent(state.getPos().asLong(), k -> new HashSet<>()).add(slotName);
}
```

**`slots` = `Long2ObjectMap<Set<String>>`，key = `BlockPos.asLong()`，value = 该位置的槽名集合。每个位置可属于多个槽。**

### 7.2 主机侧

```java
.where('B', Predicates.blocks(GTNEBlocks.MODULE_DOCK.get())
        .setSlotName("gtnecore:module"))
```

```java
public final class HostModules {
    public static List<BlockPos> slots(IMultiController host, String slot) {
        Long2ObjectMap<Set<String>> map = host.getMultiblockState().getMatchContext().get("slots");
        if (map == null) return List.of();
        List<BlockPos> out = new ArrayList<>();
        for (var e : map.long2ObjectEntrySet())
            if (e.getValue().contains(slot)) out.add(BlockPos.of(e.getLongKey()));
        return out;
    }

    public static List<IMultiController> docked(IMultiController host, String slot) {
        Level level = host.self().getLevel();
        return slots(host, slot).stream()
                .map(p -> MetaMachine.getMachine(level, p))
                .filter(m -> m instanceof IMultiController mc && mc.isFormed())
                .map(m -> (IMultiController) m).toList();
    }
}
```

**为什么必须用 `slotName`**：主机结构缓存（`state.cache`）只登记 pattern 匹配过的格子；模块控制器那一格在 pattern 里 → 在缓存里 → **模块位被破坏时主机会立刻重检**。自己事后扫就丢掉这个免费触发。

### 7.3 模块契约

```java
public interface IDockedModule {
    Block controllerBlock();                     // 主机 'B' 位要匹配的方块
    Collection<PartModule> modules();            // 装上后给主机什么贡献
    boolean canDockTo(IMultiController host);    // 装配检查（贴合面朝向等）
}
```

**主机对模块一无所知**——只要求"这个位置有个 `MODULE_DOCK` 方块"，具体是采矿还是发电由模块自己决定。

### 7.4 ⚠ 三个必须注意的约束

1. **`slotName` 会记录该谓词匹配到的所有格子**。所以 `'B'` 谓词必须**只匹配模块控制器**；写成 `blocks(casing).or(blocks(dock)).setSlotName(...)` 会把所有机壳位都变成"模块位"。
2. **两个 pattern 不允许重叠**。重叠会让两个结构互相触发重检（`MultiblockState.onBlockStateChanged` → `checkPatternWithLock`），容易打架甚至死循环。【未验证：交叠的确切行为，建议先用 3×3×3 + 2×2×2 最小例子实测】
3. **`MultiblockWorldSavedData` 按 ChunkPos 映射控制器**：`addMapping` 把结构缓存的每个 ChunkPos 都登记进 `chunkPosMapping`。若主机与模块的 chunk 有交叠，两者的重检会互相触发。

### 7.5 待定语义（影响接口形状）

| 问题 | 选项 | 影响 |
|---|---|---|
| 模块未成型时主机能否成型 | (a) 可以 (b) 必须成型 | (b) 引入两个结构的依赖顺序问题 |
| 一个模块位能否多个模块 | (a) 唯一 `setExactLimit(1)` (b) 多个 | 多个要额外编号 |
| 模块控制器能否独立运作 | (a) 依附主机 (b) 可独立 | (b) 一个方块同属两个多方块，`canShared()` 要处理 |
| 两个 pattern 允许重叠吗 | **建议不允许** | 见 7.4-2 |

## 九、已知坑速查（本次研究新发现，**建议同步进 `docs/GTCEu-API实践手册.md`**）

| # | 坑 | 证据 |
|---|---|---|
| 1 | `Predicates.abilities(...)` 是**方块快照**，不调 `isApplicable` | 字节码 |
| 2 | **空能力位 → `Blocks.BARRIER`**，结构永不成型 | `PredicateBlocks.buildPredicate` |
| 3 | `PartAbility.allBlocks` **记忆化且无 `invalidate`** | 字节码 |
| 4 | `where(String, pred)` **只取首字符**，传 `"AB"` 静默只用 `'A'` | `symbol.charAt(0)` |
| 5 | `where(char, pred)` 对非 any/air 谓词做**浅拷贝** → 同一谓词实例给两个字符会**合并计数** | 字节码 |
| 6 | `setMinGlobalLimited` 把 `common` 全搬进 `limited` 并**逐个设值** | 字节码 |
| 7 | pattern 工厂 `GTMemoizer.memoize` 永久缓存；而 `setMinGlobalLimited` 是**改字段** → 对已构建 pattern **追溯生效** | 字节码 |
| 8 | `allowFlip=true` 时匹配器在**第一个朝向**就 return 翻转结果，不再试其余朝向 | `BlockPattern.checkPatternAt` |
| 9 | `getParts()` 惰性重建路径**绕过 `shouldAddPartToController`** | 字节码 |
| 10 | `MultiblockPartMachine.getHandlerList()` 缓存**无失效机制** | 字节码 |

## 十、未决问题

1. **§7.4-2 两个 pattern 交叠的确切行为** —— 需实测。这是子结构方案的**最大技术风险**。
2. **模块粒度**：按"贡献类型"（线程/并行/热）还是按"机制"（影响配方 vs 影响结构）？倾向前者，贴合现有 `IThreadHatch` 直觉。
3. **一个部件挂几个模块** —— 若要多模块，`types()` 返回集合（本设计已按此做）；若确认单模块，可简化为单个 `type()`。
4. **`ThreadHatchPartMachine` 未重写 `canShared()`**（默认 `true`），而官方 `ParallelHatchPartMachine` 是 `false`【已验证】。是否有意为之？若是疏漏，独占语义不一致。
