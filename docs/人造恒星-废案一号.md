## 一、最终架构（撤除前那一刻的样子）

运行逻辑走**纯 GTCEu 配方系统**，这是用户明确要求的方向：
手工 `subscribeServerTick` 那套被他判定为"不符合 MC 的逻辑"，已取缔。

```
玩家灌氢/氦
   │
   ▼
输入仓（FluidHatchPartMachine）
   │  getCapabilitiesFlat(IO.IN, FluidRecipeCapability.CAP)   ← GTCEu 标准取仓方式
   ▼
StarForgeRecipeLogic（GTRecipeType.ICustomRecipeLogic）
   │  扫罐里**实际有什么**，动态生成一条配方（不写数据包）
   ▼
StarForgeMachineLogic（extends RecipeLogic）
   │  handleRecipeIO(IO.IN)：IO 前后各扫一遍罐 → 差值 = 实际消耗 → 换算质量
   ▼
StarForgeMachine.addMass(long)
   │
   ▼
质量跨过 StarTier 阈值 → 升级 / 产出选定元素的等离子体（配方真实流体输出）
```

**三个关键设计决策**（都是被逼出来的，别轻易改回去）：

1. **配方不写进数据包** —— 玩家灌多少 mB 不定，写死会产生天文数字条配方。
   用 `ICustomRecipeLogic.createCustomRecipe()` 按罐里实际内容即时生成。
2. **不读配方数据，量实际消耗** —— 配方写"最多吃 1000"，但罐里可能只有 300。
   读配方数据会让质量虚增；量 IO 前后差值则天然一致。
3. **等离子体做成配方的真实流体输出** —— 而不是手工 `tank.fill()`。
   手工 fill 会绕开配方系统，XEI 也展示不了。

## 二、踩过的坑（**这一节最值钱**）

### 坑 1 · `FactoryBlockPattern.aisle()` 的顺序会翻面 ★最致命

**症状**：结构能成型，但 `parts=0`——所有功能仓都不被认作多方块部件，
玩家把仓放在自以为对的位置也不生效。

**根因链**（这里我绕了很久，写清楚免得重蹈）：
1. aisle 没倒序 → 整个结构沿 UP 轴翻面
2. 玩家按**真实**方位摆的仓，在**翻面后**的 pattern 里落到了 `#` 位
3. 而 GTCEu 按**匹配到的字符**决定角色：`#` 格只算普通方块，**永远不会进 `getParts()`**
4. → `parts=0`，取不到任何仓

⚠️ **我当时把第 3 步误判成"漏洞"**（以为玩家能故意把仓塞进 `#` 绕开 B 位），
还去改了谓词。**那是错的**——见 §五「`#` 位的取舍」。
真凶自始至终只有 aisle 顺序。

**原因**：GTCEu 的 `aisle(...)` 是**依次往上叠**（UP 轴递增），
而用户导出的 KubeJS 结构里 `.aisle` 顺序与之**相反**。不倒序 → 整个结构沿 UP 轴翻面：

| 符号 | 用户 JS（真值） | 未倒序的生成结果 |
|---|---|---|
| `D` 控制器 | **(0, 2, 32)** | (64, 2, 32) |
| `B` 功能舱位 | 含 (0,2,32) | 含 (64,2,32) |

**修法**：生成 PATTERN 时把 65 层 aisle **整体倒序**。
`tools/fix-artificial-star-structure.py` 里已经有 `merged.reverse()`。

**复验**：`python tools/verify-star-structure.py` → `D` 必须落在 `UP=0, FRONT=2, LEFT=32`。

### 坑 2 · `setMinGlobalLimited` 会给**每一个** limited 谓词设下限

**症状**：成型要求"每种功能仓各放一个"（输入仓+输出仓+巨型输入仓+巨型输出仓+ME输入+ME输出+维护仓 全都要）。

**原因**：`TraceabilityPredicate.setMinGlobalLimited(int)` 的实现是
**遍历 `limited` 列表里的每一个谓词**，逐个设 `minCount`；
而 `.or(other)` 会把两边的 `limited` 列表**合并**。

于是这种写法：

```java
// ❌ 错误：6 个 abilities 全被设成 minCount=1
.where('B', blocks(CASING)
        .or(abilities(INPUT_ENERGY))
        .or(abilities(IMPORT_ITEMS))
        .or(abilities(EXPORT_ITEMS))
        .or(abilities(IMPORT_FLUIDS))
        .or(abilities(EXPORT_FLUIDS))
        .or(abilities(MAINTENANCE))
        .setMinGlobalLimited(1))
```

等于"6 种仓各至少一个"。

**正确修法**：把所有可接受方块**收进一个 `blocks(...)`**，只留一个谓词：

```java
// ✅ 正确：单一谓词，数量不限
.where('B', blocks(forgeHatchBlocks()))

private static Block[] forgeHatchBlocks() {
    var set = new LinkedHashSet<Block>();
    set.add(GTBlocks.HIGH_POWER_CASING.get());
    for (PartAbility ability : FORGE_HATCH_ABILITIES) set.addAll(ability.getAllBlocks());
    set.add(/* ME 输出仓 */); set.add(/* ME 输入仓 */);
    set.remove(null);
    return set.toArray(Block[]::new);
}
```

### 坑 3 · `abilities(...)` 造出的谓词在 `common` 列表里，设下限无效

**症状**：`.or(abilities(MAINTENANCE).setMinGlobalLimited(1))` 写了等于没写，维护仓下限是空的。

**原因**（字节码实证）：
`Predicates.abilities(...)` → `blocks(Block...)` → `new TraceabilityPredicate(new PredicateBlocks(...))`。
`PredicateBlocks` 的 `minCount`/`maxCount` 都是 **-1**，
而 `TraceabilityPredicate` 的构造函数是：

```java
// 反编译逻辑
if (predicate.minCount == -1 && predicate.maxCount == -1) common.add(predicate);
else                                                limited.add(predicate);
```

`-1/-1` → 落进 **common**；而 `setMinGlobalLimited` **只遍历 limited** → 静默失效。

**修法**：想让某个能力有数量下限，必须让它**单独一次** `abilities(...)` 调用
（此时它仍在 common，但 `setMinGlobalLimited` 内部会先把 common 全搬进 limited 再设值），
且**不能**和其他 `abilities` 串在同一条 `.or()` 链上。

GTCEu 自己的 `autoAbilities()` 就是这么干的——每个能力一次独立调用。

### 坑 4 · 注册 `gtceu:recipe_capability` 的合法窗口极其狭窄 ★会导致启动崩溃

**症状**：
```
java.lang.IllegalStateException: [register] registry gtceu:recipe_capability has been frozen
    at MassRecipeCapability.register(...)
    at GtnecoreMachines.onRecipeTypeRegister(...)
```
启动直接崩。

**原因**：GTCEu 的注册顺序是
```
RECIPE_CAPABILITIES.unfreeze()
  → 注册官方能力（item / fluid / EU / ...）
  → postEvent(RegisterEvent)     ← 此时各 addon 的 registerRecipeCapabilities() 被调用
  → RECIPE_CAPABILITIES.freeze()
```
而 Forge 的 `GTRecipeType` 注册事件（`onRecipeTypeRegister`）**在 freeze 之后**。

**修法**：走 `IGTAddon` 的钩子——`registerRecipeCapabilities()`：

```java
@Override
public void registerRecipeCapabilities() {
    MassRecipeCapability.register();   // 唯一合法窗口
}
```

**同类事故**：本项目 2026-09-24 的 `gtceu:cover` 冻结崩溃，
解法是 `IGTAddon.registerCovers()`。**规律：GTCEu 的注册表都只在专属 addon 钩子里 unfreeze。**

### 坑 8 · 机器模型的 `recipe_logic_status` 属性依赖配方类型

**症状**：模型变体全部失效（紫黑方块），报
`Unknown machine model state property: 'recipe_logic_status'`。

**原因**：`recipe_logic_status` 这个渲染属性只在机器**有配方逻辑时**才存在。
无配方类型的机器只有 `is_formed` 两个变体。

**规律（写任何 GTCEu 机器都要先查这一组三件套，它们**强耦合**）**：
```
rotationState  ⇄  blockstate 变体  ⇄  模型变体
```

| 机器类型 | blockstate 变体 | 模型变体 |
|---|---|---|
| 有朝向 | `facing=east/north/south/west` | — |
| 有配方类型 | — | `is_formed` × `recipe_logic_status` = 8 个 |
| 无配方类型 | — | `is_formed` ×2 |

### 坑 9 · `Material.getFluid(key, amount)` 返回 `Fluid`，不是 `FluidStack`


### 3.1 取多方块的流体/能量仓


## 五、结构谓词（撤除前的最终版）

```java
.where('D', controller(blocks(controllerBlock)))          // 控制器
.where('A', blocks(GTBlocks.HIGH_POWER_CASING.get()))     // 球壳
.where('E', blocks(GTBlocks.MACHINE_CASING_UHV.get()))    // 球内填充
.where('F', blocks(/* avaritia:neutron */))               // 中子核心
.where('B', blocks(forgeHatchBlocks()))                   // 功能舱位：任一即可，数量不限
.where('#', Predicates.any())                             // 空洞：选择性无视
```

**`#` 位的取舍 —— 曾经虚惊一场，现已证伪（2026-09-26 用户实测）**

我一度认为 `Predicates.any()` 是个漏洞：玩家把功能仓塞进 `#` 区域就能绕开 B 位、
结构照样成型照样可用，还一度改成「拒绝一切 `IMachineBlock`」。

**❌ 这个判断是错的。** 用户实测结论：

> **放在 `#` 位的功能仓，多方块根本不把它当舱室，只认作普通方块。**

**原因**（想明白就通了）：GTCEu 是按**匹配到的 pattern 字符**决定角色——
匹配到 `B` 的格子才走 `abilities`/部件收集路径；匹配到 `#` 的格子只是一次
普通方块替换。所以 `#` 里的仓**永远不会进 `getParts()`**，也就永远不会被当部件用。

**结论**：
- `Predicates.any()` **安全**，不需要任何防护，也不必改成 `custom` 拒绝机器方块
- 之前我看到的 `parts=0` **不是这个原因**造成的，真凶是 **坑 1（aisle 顺序翻面）**：
  结构翻面后，玩家摆仓的位置在 pattern 里对应到 `#`，于是不被认作部件——
  现象一样，病因完全不同。**我把结果对了、原因猜错了。**
- **`#` 位有 169,645 格**，用 `air()` 会逼玩家清空整片区域（不现实），所以 `air()` 同样不可取

**重做时**：`#` 用 `Predicates.any()` 即可，别再加防护逻辑。
