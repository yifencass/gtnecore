## 一、超净间环境机制（源码验证结论）

GTCEu 的超净间既不是全局注册表、也不是每 tick 空间扫描，而是：

**成型期空间扫描 + 直接引用绑定（Direct Reference Binding）**

```
超净间 onStructureFormed（成型）
  → pattern 的 innerPredicate 扫描内部空位（capability 查询收集接收者）
  → 对每个内部机器调 receiver.setCleanroom(this)（把自身引用塞进机器字段）
之后机器判断"是否在超净间"：只读自己缓存的 cleanroom 引用 → isClean() && getTypes().contains(type)
```

### 1.1 关键接口（javap 验证签名）

```java
ICleanroomProvider { Set<CleanroomType> getTypes(); boolean isClean(); }        // 提供者
ICleanroomReceiver { ICleanroomProvider getCleanroom(); void setCleanroom(p); }  // 接收者
CleanroomType       // public 构造器 (String name, String translationKey) 即自注册进
                    // static Map<String, CleanroomType>；CODEC 按名序列化；
                    // getByName / getByNameOrDefault / getAllTypes
```

- **接收者零成本**：`IRecipeLogicMachine extends ICleanroomReceiver`——所有配方机器
  （多方块/单方块/蒸汽机）天然是接收者；`MetaMachineBlockEntity.getCapability` 对
  `CAPABILITY_CLEANROOM_RECEIVER` 返回 machine
- **检测链**：`RecipeLogic.checkRecipe → RecipeHelper.checkConditions →
  CleanroomCondition.testCondition`（验证：`provider.isClean() && provider.getTypes().contains(this.cleanroom)`）。
  配方侧 `builder.cleanroom(CleanroomType)` / JSON `"cleanroom": "<name>"`

### 1.2 结构与动态尺寸（CleanroomMachine 源码）

- **动态房间**：`updateStructureDimensions()` 从控制器向 4 水平向 + 向下扫描
  （`isBlockEdge` = casing 或玻璃；`isBlockFloor` 另含 `CLEANROOM_FLOORS` 标签），
  得 lDist/rDist/bDist/fDist/hDist（最小 2×2 半径、深 4），`getPattern()` 按尺寸
  现场拼 aisles——**变体改墙体只需覆写 `getCasingState()`/`getGlassState()`**
- **墙体谓词**：`'W'` = wall 谓词（casing/玻璃/能源仓≤2/维护≤1/贯通仓≤面积¼）
  `.or(goetyApparitionDoor()≤6)`（GTNEcore 幻影门）`.or(doorPredicate()≤8)`（CLEANROOM_DOORS 标签）
- **顶棚过滤器定类型**：`'F'` = `Predicates.cleanroomFilters()`（遍历
  `GTCEuAPI.CLEANROOM_FILTERS: Map<IFilterType, Supplier<Block>>`），匹配时把
  `IFilterType` 写进 match context；`onStructureFormed` 读 `"FilterType"` →
  `cleanroomType = filterType.getCleanroomType()`（**自定过滤器 = 自定环境类型的现成通道**）
- **内部判定**：`innerPredicate()`（protected，可覆写）收集接收者 + `isMachineBanned()`
  （protected）拦截禁入机器（发生器/采矿/原始机械/另一个环境提供者）

### 1.3 供电与生效（CleanroomLogic 源码）

- 清洁时耗 `max(8, 3/16 V[tier])` EU/t，脏时 `VA[tier]`（≈15/16 安）
- 每周期 ±`(2 + 3×(tier-LV+1))` 清洁度（维护问题每个 -1）；满 95 即 `isClean()`
- 维护问题 ≥6 或处于环境污染区（EnvironmentalHazardSavedData zone）→ 只衰减不清洁
- 成型但断电的超净间**不提供环境**（isClean=false → 条件不过）

### 1.4 原版注册链（GTMultiMachines 字节码还原，变体照抄骨架）

```java
CLEANROOM = GTRegistration.REGISTRATE
    .multiblock("cleanroom", CleanroomMachine::new)
    .rotationState(RotationState.NONE)          // 无朝向（NONE 机器成型检测水平 4 向）

```

### 1.5 扩展面清单（变体可用钩子，全部验证为 public/protected）

| 钩子 | 可见性 | 变体用途 |

## 二、变体 A：天文研究台（Astronomical Room）

**结论：完全可行**，`AstronomicalRoomMachine extends CleanroomMachine`（patch 层类
public、钩子 protected/public，主工程可直接继承）。

### 2.1 骨架

```java
public class AstronomicalRoomMachine extends CleanroomMachine {
    public static final CleanroomType ASTRONOMICAL =
            new CleanroomType("astronomical_observation", "gtnecore.recipe.astronomical.display_name");

    @Override protected BlockState getCasingState() { return 观测塔机壳; }
    @Override protected BlockState getGlassState()  { return 观测穹顶玻璃; }
    @Override public Set<CleanroomType> getTypes()  { return Set.of(STERILE?, ASTRONOMICAL); }
    // onStructureFormed 强制 cleanroomType = ASTRONOMICAL（不走过滤器）
}
```

- 内部配方机自动绑定 → 环境按 getTypes() 提供（供电门控同超净间）
- 新配方 `.cleanroom(ASTRONOMICAL)` / JSON `"cleanroom": "astronomical_observation"` 直接可用
- **类型语义二选一**：`Set.of(ASTRONOMICAL)`（天文研究台是独立环境，内部机器不再享受
  普通超净加成）或 `Set.of(CLEANROOM, ASTRONOMICAL)`（一屋两用）。推荐**独立环境**——
  避免天文台内部机器被普通超净配方蹭用
- 顶棚若不用过滤器：覆写 `getPattern()` 把 `'F'` 换成观测穹顶方块 + `onStructureFormed()`
  强制类型；若想复用过滤器机制：实现 `IFilterType.getCleanroomType() → ASTRONOMICAL` +
  `GTCEuAPI.CLEANROOM_FILTERS.put(type, 方块)`（注意过滤器对普通超净间也可见，会分流）

### 2.2 观测状态（夜间/天空可见门控）

原版已有 `DaytimeCondition`（"daytime": true/false）可直接叠加；若要"正在观测"
（星图装载 + 夜间 + 无遮挡）运行时状态，加轻量标记接口（不扩 ICleanroomProvider，
保持二进制兼容）：

```java
public interface IAstronomicalObservationProvider { boolean isObserving(); }
```

`AstronomicalObservationCondition extends RecipeCondition` 检测
`receiver.getCleanroom() instanceof IAstronomicalObservationProvider p && p.isObserving()`，
`RecipeConditionType` 注册进 `GTRegistries.RECIPE_CONDITIONS`（addGenericListener 套路
同机器注册，名字如 `"astronomical_observation"`）。

### 2.3 与发射台控制器通信（三档，沿用原设计）

1. **直接引用绑定（推荐，GTCEu 风格）**：天文控制器成型/定期在限定半径找发射台
   控制器，持有 MetaMachine 直接引用，`@Persisted` 存坐标断链恢复
2. **世界级 SavedData 注册表**：远距离/多实例/跨维度
3. **Forge Capability**：`IAstronomicalLink` 由发射台提供

### 2.4 实现状态（2026-08-27，v1 已落地）

- **天文辅镜** `gtceu:astronomical_finderscope`：纯建材方块，顶面合成贴图
  （`scripts/composite_finderscope_top.py`，plascrete 底 + 镜片 overlay）
- **天文观测站** `gtnecore:astronomical_observatory`（`AstronomicalObservatoryMachine`
  extends CleanroomMachine + `AstronomicalLogic` extends CleanroomLogic）：
  - 固定 9×9×5 pattern（KJS 示意转写，`createPattern`）。**轴语义坑**：
    `FactoryBlockPattern.start(charDir, stringDir, aisleDir)`——KJS 无参默认
    `start(LEFT, UP, FRONT)`：字符串=上下（每 aisle 5 行=5 格高）、aisle 沿前后
    （9 个=9 格深）。传 `start(LEFT, FRONT, UP)` 会让整个结构竖起来（首次注册
    就是这样错的）。结构：plascrete 地/墙（A）、地面能源仓 1..8（B）、玻璃墙/
    通行仓/幻影门≤7（C）、辅镜顶棚环带（D）、**顶面中心控制器**（E，NONE
    不可旋转，四周 8 块 plascrete 成 3×3 顶面环）、地面维护仓≥1（F）、内部
    接收者空腔（#）
  - 校准 = 超净间清洁度：成型后耗 VA[tier]/t 校准（周期 200t，增益 2+3×(档位-LV+1)），
    校准度 ≥95 → 低功耗（3/16 V[tier]）+ 提供 ASTRONOMICAL 环境
    （`CleanroomType("astronomical_observation")` 自注册，配方 `.cleanroom()` 直接可用）
  - **无线供电**：`wirelessPowerTick()` 每 tick 把能源仓 EU 推给内部接收机器
    （每台上限 2×VA[tier]，`GTCapabilityHelper.getEnergyContainer` 查询目标）
- 待定：控制器 3×3 跨方块大图（路线 A DynamicRender / 路线 B 九宫格，见 §2.5）

### 2.5 无线供电实现方式探索（为后续通用体系铺路）

**本次采用：推送式（push）房间级供电**
- 源：控制器 `initializeAbilities()` 收集的 `EnergyContainerList`（能源仓）
- 目标：成型期 `innerPredicate` 收集的接收机器（`ICleanroomReceiver` 集合），
  每 tick `getEnergyContainer(level, pos, null)` 查其 EU 容器并注入
- 语义：`addEnergy()` 返回实际注入量，按实际值 `removeEnergy()` 扣源（防溢出丢电）；
  配额 = 每机每 tick 2×VA[档]
- 优点：零注册表零持久化，绑定随成型/失效自然建立/解除（超净间接收者同款生命周期）
- 局限：只覆盖结构内部；无跨结构/跨维度；每 tick 遍历（机器少时可忽略）

**未来通用无线供电三档方案**：
1. **推送式网格**（本实现推广）：定义 `IWirelessPowerProvider`，提供者每 tick 向
   登记的接收者推送；接收者通过事件/接口登记（房间级，最简单）
2. **拉取式能力查询**：机器缺电时反向查询附近 provider（世界级缓存 + 失效重扫，
   类似 CleanroomReceiver 的懒查询）；省 tick，但要处理缓存失效
3. **全局网格 SavedData**：发/收两端注册进世界级注册表（MultiblockWorldSavedData
   模式），按 tick 配额结算，支持跨结构/跨维度/距离衰减——可做成独立"无线能源网格"
- 共同细节：转移按实际注入量结算；每 tick 总配额防炸服；引用 + 坐标双持防断链

## 三、变体 B：实验室（Laboratory）

**结论：同骨架直接可行**，差异只在语义与外观：

```java
public class LaboratoryRoomMachine extends CleanroomMachine {
    public static final CleanroomType LABORATORY =
            new CleanroomType("laboratory", "gtnecore.recipe.laboratory.display_name");
    // 换实验台机壳/防爆玻璃墙体；getTypes() = Set.of(LABORATORY)
    // 可覆写 createRecipeLogic 换更贵的供电曲线（如清洁期 2×VA、维护问题直接清零清洁度）
}
```

- 定位：**专属配方门槛**（如生物培养/化学合成类配方只在实验室环境可跑）+
  视觉区分；机制 100% 复用超净间
- 可选强化：`isMachineBanned` 覆写加严（如禁一切发生器/动力机器，只留研究机），
  或与环境污染系统联动（实验室处于污染区 → 无法成型/加倍衰减，CleanroomLogic 已有
  zone 判定可直接利用）
